# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It covers `backend/`.

System-wide architecture, database boundaries, API standards and the roadmap are in the root `CLAUDE.md` and `Architecture.md`. Setup, environment variables and provider configuration are in `README.md`. How the security works is in `spec/security/design.md`; the usage limits are specified in `spec/usage/spec-usage.md` (the weekly Ask AI allowance in `spec/weekly-ask-ai-limit/spec.md`) and Ask AI in `spec/ask-ai-backend/spec.md`. There is no linter or formatter configured: `./mvnw clean test` is the only check.

## Gotchas

- **Use `./mvnw clean test` after changing a constructor or signature.** An incremental build keeps stale test classes and can hide compile errors.
- **`server.forward-headers-strategy` must stay `native`.** With `framework`, Spring 7 lets any client choose its own IP and dodge the rate limits.
- **Passwords are limited to 72 bytes** (bcrypt in Spring Security 7 rejects more). Do not raise `PasswordPolicy` limits without changing the encoder.
- **A class with two constructors needs `@Autowired` on the injection one**, otherwise the context fails with "No default constructor found" (this is the one exception to "no `@Autowired`").
- **Tests that start many analyses as one user need the high free-tier limit.** `application-test.properties` raises `archyra.usage.free-tier.*` to 100000; only the `Usage*IntegrationTest` classes bind the real small limits. The reset zone (`archyra.usage.reset-zone`) is the application default (`Asia/Kolkata`) in tests too. Starting the same repository URL again while it still runs returns the running analysis, so a test that wants two analyses must use two URLs.
- **`redirect_uri_mismatch` is a provider-console problem, not a code one.** With `forward-headers-strategy=native` and the dev proxy's `Host`/`X-Forwarded-*`, the redirect URI is `http://localhost:5173/login/oauth2/code/{google,github}` (`OAuth2RedirectUriHttpTest` pins it over real HTTP; never hard-code a redirect URI). A GitHub OAuth App accepts one callback URL, Google several. See `README.md` → Provider set-up.
- **The development PostgreSQL must be a pgvector build** (e.g. `pgvector/pgvector:pg17`); a plain `postgres` image stops startup with a message. The application runs `CREATE EXTENSION IF NOT EXISTS vector` before Hibernate's schema update (`ai/PgVectorSetup`, an `EntityManagerFactoryDependsOnPostProcessor`), because an `ApplicationRunner` would be too late.
- **The embedding model is not in the `spring-ai-transformers` jar** (its `model.onnx` is a 133-byte pointer). Run `./scripts/fetch-embedding-model.sh`, or let the first start download it into `models/` (git-ignored). `EmbeddingService` loads it lazily; `archyra.ai.embedding.verify-on-startup=true` (false in tests) loads it at startup.
- **A killed test container looks like a flaky test.** If whole classes fail with "expected COMPLETED but was FAILED" and `Unable to connect to localhost:<port>` in the log, check `docker events --filter event=oom` and the Docker VM's memory before touching code.
- **A provider's base URL ends where `/chat/completions` can be appended** (Groq's is `https://api.groq.com/openai/v1`, so it ends in `/v1`; Cloudflare's contains the account id, and a base URL with an empty segment, an unset `CLOUDFLARE_ACCOUNT_ID`, makes the provider "not configured"). Spring AI's auto-configuration is not used on purpose (Gemini is an explicit `Google GenAI` model, everything else a plain `RestClient`; no default `ChatModel`).
- **A test dependency fell out of the classpath once**: Spring AI's ONNX dependency (DJL) brings `commons-compress` 1.27.1 closer to the root than the 1.28 Testcontainers needs, which dropped `commons-lang3` and broke Testcontainers' client; it is declared in `pom.xml` for tests.
- **"Could not connect to Ryuk"** in a test run is a Docker/Testcontainers hiccup. Rerun before debugging.
- The `.env` file is git-ignored and `.env.example` lists the variables. Run everything from `backend/`, since `.env` and `native/` resolve against the working directory.

## Package conventions

The base package is `com.abhiraj.archyra`, organised by feature (package-by-feature), not by layer.

- Only feature packages and `common/` sit directly under the base package. Never create root-level `controller/`, `service/`, `repository/`, `dto/` or `entity/`.
- Keep a feature's classes flat; add a subpackage only when it grows large (as `parsing/lang/` and `auth/oauth2/` did).
- A class lives in the feature that owns its use case. Shared code goes to `common/` only when two or more features need it, never to a generic `util/` or `helpers/`.
- Features talk through public services and IR/DTO types, never through another feature's repositories or internals. Repositories are package-private where possible.
- A new feature gets a new top-level package and the tree below is updated in the same change.

```
com.abhiraj.archyra
├── analysis/      # Analysis lifecycle: /api/v1/analyses (create, list, status, delete, reanalyze, analyze a restored entry), ownership, AnalysisRegistrar (the only way to create or delete one), AnalysisRestoreService (NOT_ANALYZED entries for a returning user), AnalysisActivity (last_activity_at) and AnalysisRetention (which repositories a lapsed user keeps), AnalysisSchemaUpgrade, background AnalysisPipeline
├── ingestion/     # Clone repository, file discovery, language detection
├── parsing/       # TreeSitterExtractor base, ParsingService, ReferenceResolver (IR → code graph IR)
│   └── lang/      # one extractor (and, where imports differ, one ModuleResolver) per language
├── technology/    # Frameworks, libraries, tools: technologies.tsv catalog, manifest reader, detector
├── ir/            # Archyra Intermediate Representation: plain language-agnostic model
├── graph/         # IR → Neo4j builder, graph queries, /graph and /nodes endpoints, premium gate
├── codebase/      # Read endpoints: /repository (languages, counts and the detected technologies as `TechnologyResponse { name, category }`), /files, /classes
├── user/          # Accounts, linked social identities, /users/me, admin API (/admin/users, incl. PUT /{id}/plan); UserService is the entry point
├── auth/          # /api/v1/auth, refresh-token rotation, email flows, password change (/users/me/password), token purge, admin bootstrap
│   └── oauth2/    # Google and GitHub login: second filter chain, account resolver, handlers; account linking (link intents, binding cookie, link-mode handler, /users/me/linked-identities)
├── mail/          # EmailService and the asynchronous SMTP implementation
├── ai/            # Ask AI (V1): /ai-index endpoints, pgvector setup, the listeners of the pipeline events, AiProperties
│   ├── index/     # chunk capture, local ONNX embeddings, code_chunks / ai_index, embedding job, recovery sweeper, ChunkSearch
│   ├── retrieval/ # hybrid retrieval: name lookup, vector search, graph expansion, ranking and token budgets
│   ├── llm/       # the provider chain: ProviderRegistry (config blocks → providers), GeminiChatProvider + OpenAiCompatibleChatProvider, ProviderGuard (local limits), ProviderCooldowns, ProviderGateway (fallback); the only way to a model; GET /admin/ai/providers
│   └── chat/      # POST /chat, conversations, quota reservation and refund, prompt, grounding, answer cache
├── billing/       # Premium through Razorpay: /api/v1/billing (plans, status, retention, payments, orders, subscriptions, the public webhook), RazorpayGateway (RestClient) + PaymentSignatures, BillingService.applyPayment (the one place that extends Premium), SubscriptionService, PremiumLifecycleJob (reminder, expiry notice, end of grace)
├── usage/         # Usage counters (user_usage: lifetime for analyses, weekly for Ask AI), UsageWindows (the Monday 00:00 week), free-tier limits from configuration, GET /api/v1/usage, the usage ledger (usage_ledger counts, usage_ledger_repository links) that survives account deletion
├── security/      # Properties, JWT, API filter chain, rate limiting, entitlements, audit log
└── common/        # Exceptions and their handler, shared config (clock, async, scheduling, Tomcat), TestPathClassifier (is this path test code?), the pipeline events (AnalysisGraphBuilt, AnalysisCompleted, AnalysisFailed, AnalysisDeleting), AccountDeleted
```

- Controllers are thin: validate, call a service, map to a DTO. They never return JPA or Neo4j entities.
- Request and response DTOs are `record`s. Lombok is for boilerplate only (`@Getter`, `@Builder`, `@RequiredArgsConstructor`, `@Slf4j`); no `@Data` on entities.
- Constructor injection only (`@RequiredArgsConstructor`, `final` fields); see the `@Autowired` exception under Gotchas.
- Enums from `Architecture.md` are Java enums named exactly like the API values: `AnalysisStatus`, `NodeType`, `RelationshipType`, later `ExpertiseLevel`.

## Endpoint and pipeline rules

- Routes live under `/api/v1`; per-endpoint behaviour is in `Architecture.md` next to each endpoint. `POST /analyses` returns `{ analysisId, status: "QUEUED" }` immediately; the pipeline runs `@Async` on a dedicated bounded executor (no Redis or RabbitMQ yet).
- Validation: Jakarta Validation on request records plus `@Valid`. `repositoryUrl` must be `https://github.com/{owner}/{repo}` (no other scheme or host, no `..`, no credentials). Bound every user-controlled query parameter.
- Ingestion: shallow clone (`--depth 1`) into a per-analysis temp directory, always deleted in `finally`. Enforce file-count and size limits; skip binaries, vendored code and build output.
- A single `@RestControllerAdvice` in `common/` maps one exception per outcome to `{ code, message }`. Messages never echo user input.

## Usage limits

Free users have a lifetime allowance of analyses and a **weekly** allowance of Ask AI questions (`archyra.usage.free-tier.*`, never a literal in code); `usage/` holds the counters, `analysis/` and `ai/chat` consume them. Full semantics: `Architecture.md` → Usage and "Decision: Ask AI questions are a weekly allowance".

- **All analysis creation must go through `AnalysisRegistrar`; never call the pipeline directly.** The registrar locks the user's `user_usage` row, checks for a running duplicate, checks the limit, increments and inserts the analysis in one transaction. `AnalysisService.createAnalysis` itself stays non-transactional.
- **A new way to start an analysis must use `registrar.registerOrReuse`.** `reanalyze` does: `AnalysisService.start` is the shared path, and a re-run passes the finished analysis it replaces, which `AnalysisCleanup.deleteReplaced` removes only after the new one is `COMPLETED` (it never throws and only touches a finished analysis of the same owner). Anything that ends an analysis as `FAILED` must use `registrar.failAndRefund` (or `refundQuota`), which is idempotent.
- `UsageService.lock`, `charge` and `release` are `MANDATORY`-transactional on purpose: a unit is charged or released in the caller's transaction, never on its own. `AI_QUERY` is consumed by Ask AI (see below); a new type needs an enum value (with its `weekly` flag) and one limit in `UsageProperties`, whose exhaustive switch will not compile without it.
- **`AI_QUERY` is weekly and resets lazily, with no scheduler** (`spec/weekly-ask-ai-limit/spec.md`). `UsageType.weekly()` marks it; a weekly row's `window_start` is the Monday 00:00 (in `archyra.usage.reset-zone`, default `Asia/Kolkata`, validated at startup) its `used_count` belongs to. `UsageService.lock` and `charge` compare it with `UsageWindows.currentStart()` (an injected `Clock`; `ZonedDateTime` on local dates, never `+ 7 * 24h`) and roll the locked row over to 0 inside the same transaction; reading (`usageOf`) does the arithmetic without writing. A null `window_start` (a row from before the change) is an old window. **Never reset counts with a job, and never compute the week with `Instant` arithmetic.** `UsageEntry.resetsAt` and the `403` body (`UsageLimitExceededException.resetsAt` → `ErrorResponse.resetsAt`) exist only for weekly types.
- **A weekly refund goes to the window it was charged in.** `charge` returns that window; `ChatTransactions.reserve` stores it in `chat_messages.quota_window_start`; `refund` reads it before the exactly-once guard and calls `release(user, type, window)`, which is a no-op once the window is over or when it is null (a message charged before the change) and otherwise a guarded `UPDATE ... WHERE window_start = :window AND used_count > 0`. The two-argument `release` is for lifetime types only and refuses a weekly one. A new consumer of a weekly type must keep the returned window with the reservation.
- **The ledger keeps the window of a weekly count** (`usage_ledger.window_start`; `UsageLedgerService.record` stores it, `restoreFor`/`restoreInto` restore a weekly count only for the current window, and the upserts `raiseToInWindow` replace an older window, keep the larger count within one window, and never lower a newer one). Weekly and lifetime types use separate native statements, so no statement has to bind a null window.
- **Deleting an account keeps the consumption** (`usage/UsageLedgerService`, `spec/account-deletion/spec.md` and its amendment). `AccountDeletionService` writes the user's per-type `used_count` and the URLs of the analyses that still hold a credit (`AnalysisPurgeService.retainableRepositories`: `quota_charged` and not `quota_refunded`) into `usage_ledger` / `usage_ledger_repository` first, **overwriting** what the keys held (`UsageLedgerService.record`: the current count, or no row at 0; the key's repository rows deleted and re-inserted), never `greatest()`: the maximum rule is for restore and merge only (under HMAC-SHA256 keys of the email and every linked identity, secret `USAGE_LEDGER_SECRET`, at least 32 bytes), then removes the analyses through **`AnalysisPurgeService`, which never refunds** (guarded by `AccountDeletionPurgeIntegrationTest`), then the tokens, identities, counters and the user. **Every code path that creates a user, or attaches an identity to one, must call the ledger in the same transaction** (`UserService.registerIfAbsent`, `createSocialUser(.., provider, id)`, `mergeLedgerUsage`, `IdentityLinkService.link`): the restore takes the maximum per type and only raises counts, then `AnalysisRestoreService.restoreFor` (same transaction) creates the not-analysed entries (below). `UsageLedgerService` writes `user_usage` through a `greatest()` upsert; nothing else besides `UsageService` may touch `user_usage`. The ledger stores no plan (a returning user is FREE), never a raw email, key or hash in a log or a response, and registration, login and OAuth answer identically with or without a match. The ledger secret must stay stable: changing it makes old entries unmatchable.
- **Restored `NOT_ANALYZED` entries** (decision: `Architecture.md` → "A returning user gets their repositories back as not-analysed entries"). `UserService` (registration, first social sign-in, `mergeLedgerUsage`) and `IdentityLinkService.link` call `AnalysisRestoreService.restoreFor(userId, keys)` right after `restoreInto`; it creates at most `used count - credits already held` entries (union over the keys, the largest per-key multiplicity per URL, never a repository the account already holds, newest first) **only through `AnalysisRegistrar.registerRestored`**, which charges nothing (the count already includes the credit). `UserService` reaches it through an `ObjectProvider` because a constructor dependency is a bean cycle (registrar → `UsageService` → `EntitlementService` → `UserService`). `NOT_ANALYZED` is idle: **`Analysis.isInProgress()` (queued or running) is what "still running" means; `isFinished()` is COMPLETED/FAILED; a new place that asks either must decide what a `NOT_ANALYZED` row does** (it is not in `IN_PROGRESS`, `AnalysisRecovery` excludes it, `AnalysisPurgeService` removes it without blocking the deletion, `requireCompleted` answers `409 ANALYSIS_NOT_COMPLETED` for it, `reanalyze` refuses it, and a pipeline can never advance, complete or fail it: `Analysis` throws). `POST /analyses/{id}/analyze` (`AnalysisService.analyze`): owner check, status check, the `CREATE_ANALYSIS` rate limit, then `registrar.startRestored` (user usage-row lock, then the guarded `UPDATE ... status = QUEUED WHERE status = NOT_ANALYZED`; losers get `409 ANALYSIS_NOT_RESTORABLE`), then the pipeline; a rejected queue calls `returnRestored` (back to `NOT_ANALYZED`, **no refund, no failure**); a later failure is the ordinary `failAndRefund`. **Never charge in that path** and never add a second refund path: deleting an entry is `deleteAndCredit` (whose row delete is guarded by `deleteIfIdle`, so a delete cannot pull a row from under a just-started run). **`analyses.status` has a Hibernate CHECK that `ddl-auto=update` never widens**: `AnalysisSchemaUpgrade` rebuilds it from the enum at every start (idempotent; `AnalysisSchemaUpgradeIntegrationTest` puts the old one back); **adding an `AnalysisStatus` value needs no change there, but any other place that lists statuses does**. No log line may carry a repository URL next to a user id or key.
- **Account deletion and Neo4j.** Neo4j is outside the PostgreSQL transaction and its client misbehaves when called from a transaction's completion callback (a graph delete inside `afterCommit` silently did nothing), so `AccountDeletionService.delete` returns a `Deleted` and the caller runs `afterDeletion` **after** the transaction has committed, outside any transaction: it revokes the access token (`security/RevokedSubjects`), drops the graphs (`AnalysisPurgeService.dropGraphs`), audits and emails. The ids are written to `pending_graph_purges` in the deletion transaction and a sweep retries what could not be dropped. An analysis still running makes the deletion a `409 ANALYSIS_IN_PROGRESS`.
- **Deleting an analysis gives its credit back to a free user.** Every deletion goes through `AnalysisCleanup.delete` → `AnalysisRegistrar.deleteAndCredit` (refund guard plus row delete in one transaction); never delete an `Analysis` row any other way. Premium users, `FAILED` analyses (already refunded) and pre-usage rows return nothing.
- `Analysis` is `@DynamicUpdate`. Keep it so: a full-row save would overwrite `quota_refunded` with a stale value and allow a second refund.
- `GET /usage` returns `UsageResponse { plan, usage: [UsageEntry { usageType, used, limit, remaining, limitReached, resetsAt }] }`; `limit` and `remaining` are `null` for PREMIUM; `resetsAt` (ISO-8601 instant of the next reset) is left out for lifetime types.
- **Weekly-reset tests move time with `MovableClockConfig`** (a `@Primary` `MovableClock` for the whole context, JWT and plan expiry included; `WeeklyUsageIntegrationTest`, `AccountDeletionIntegrationTest`). Never import it into a Chat/AI test class: provider cool-downs need real time to pass. Without it, a real-clock test must not assert a literal Monday (`ChatQuotaIntegrationTest` checks that `resetsAt` is a future Monday 00:00 in the zone).
- Usage integration tests extend `UsageIntegrationSupport` (stubbed pipeline) and use latches and barriers, never sleeps. Tests that create several analyses for one user must use a fresh user per test, because a free user stops at the limit.

## Billing (`billing/`)

Premium through Razorpay. Spec: `spec/razorpay-premium/spec.md`; decisions and API: `Architecture.md` → Billing and "Decision: Premium through Razorpay".

- **Razorpay is behind `RazorpayGateway`**, implemented by `RazorpayRestGateway`, a plain `RestClient` with HTTP Basic (`key_id:key_secret`). Not the official `razorpay-java` SDK: it hard-codes `https://api.razorpay.com` (no base URL to point at WireMock) and brings OkHttp 3.10 with a logging interceptor. Tests use `FakeRazorpay` (WireMock speaking Razorpay's wire format) through `archyra.billing.razorpay.base-url`; nothing else is faked. `logging.level.org.springframework.web.client=INFO` is pinned because `RestClient` logs request bodies at DEBUG.
- **`BillingService.applyPayment` is the only code that extends Premium.** Every confirmation (checkout verify, `payment.captured`, `order.paid`, `subscription.charged`) calls it; it compares amount and currency with our `payments` row, locks the user (`UserService.lockForUpdate`), and lets one caller through with the guarded `PaymentRepository.markPaid` (`CREATED`/`FAILED` → `PAID`). New expiry = `max(now, end) + one calendar period` in `archyra.billing.zone` (`BillingPeriod.addTo`, `ZonedDateTime`, never hours). **Do not add `clearAutomatically` to the payment updates**: it detaches the locked `User` and the new plan is silently not written (it happened). A subscription charge is a `payments` row inserted with its Razorpay payment id (`insert ... on conflict (razorpay_payment_id) do nothing`), so the verify call and the webhook extend once between them.
- **The webhook** (`BillingWebhookController`, the only public billing route, CSRF-exempt by name in `SecurityConfig`, listed in `EveryEndpointIsProtectedTest`): per-IP rate limit, body read as raw bytes up to 64 KiB, `X-Razorpay-Signature` HMAC over those bytes before parsing (`PaymentSignatures`, `MessageDigest.isEqual`), every refusal a bare `400`. `BillingWebhooks.handle` claims `X-Razorpay-Event-Id` in `webhook_events` in the same transaction as the work (a failure rolls the claim back so Razorpay's retry runs it). Orders are matched through our payment row, subscriptions through our `subscriptions` row, never through the payload alone. A refund is recorded only; `PUT /admin/users/{id}/plan` is the tool.
- **`PremiumLifecycleJob`** (`archyra.billing.sweep-interval`, the injected `Clock`): reminder (`reminder-days` before), expiry notice, and at the end of the grace period, in one transaction: lock the user, **re-read the end** (a renewal stops it), `usage.lock` (serialises with analysis starts), `AnalysisRetention.rank` and `AnalysisPurgeService.purgeSelected` (**no refund**, the `purgeAllOf` internals), plan to FREE with no end; graphs dropped after the commit. Each step is claimed by inserting its `billing_notices` row (`(user_id, kind, period_end)` unique) and only the inserter acts. Users whose subscription will charge again (live, not cancelled; halted does not count) are skipped. **The grace period runs from the expiry notice when that went out more than an hour late** (`BillingService.graceEndsAt`): nobody loses a repository without having been told the date. The job's purge listeners clear the persistence context, so the user row is read again before the plan changes.
- **Activity** (`analyses.last_activity_at`, `AnalysisActivity.touch`, a guarded UPDATE at most once per `touch-interval`, its own transaction, never throws): on creation (`AnalysisService.start` and `analyze`), on completion (pipeline), on every open (`requireCompleted`, after the ownership check) and for every answered or cached Ask AI question (`ChatService`). `AnalysisActivityBackfill` fills null rows at startup. `AnalysisRetention.rank` is the one ranking for the warning (`GET /billing/retention`, emails) and the deletion.
- **Account deletion** publishes `common/AccountDeleted` after the commit; `BillingAccountEvents` cancels a live subscription at Razorpay at once (best effort; the sweep's `cancelOrphans` retries) and drops the user's notices. Payments are kept (ids and amounts, nothing personal).
- **Tests**: `BillingIntegrationSupport` (real pipeline with only `GitCloner` replaced, PostgreSQL, Neo4j, `MovableClockConfig`, the mail recorder, `FakeRazorpay`, real HMACs with test secrets; `RazorpayEvents` builds webhook bodies in Razorpay's format). The job sweeps every user of the shared test database, so assert on one user, never on run totals. `application-test.properties` blanks the Razorpay values (billing off unless a test turns it on) and raises the billing rate limits. Never log a key, a signature, a body, an email or an amount; `BillingWebhookIntegrationTest` checks the failure paths.

## Analysis pipeline

`AnalysisPipeline` runs on `analysisExecutor`: `CLONING` (5%) → `PARSING` (25%) → `ANALYZING` (60%) → `BUILDING_GRAPH` (80%) → `COMPLETED` (100%), each step a short write to PostgreSQL. Stages: `IngestionService` → `ParsingService` (one `LanguageExtractor` per file) → `ReferenceResolver` (whole-repository second pass, IR → `CodeGraphIR`) → `GraphBuilder` (batched Cypher). Graph semantics (ids, relationships, external nodes) are in `Architecture.md` → Notes.

- Anything thrown ends the analysis as `FAILED`, together with returning its usage unit (one transaction). Throw `AnalysisFailureException` for expected failures: its message is stored and shown to users, so no paths or internals. Other errors get a generic reason; details go to the log.
- Never hold a database transaction while the pipeline runs, and keep `AnalysisService.createAnalysis` non-transactional: the row must be committed before the pipeline thread loads it.
- A half-written graph is deleted when `BUILDING_GRAPH` fails. `AnalysisRecovery` marks analyses left in progress by a restart as `FAILED` (single instance assumed).
- One unparsable file never fails the analysis; a repository with nothing parsable fails with a reason that lists the supported languages.

## Read endpoints

Every read endpoint follows one path, so a new one should reuse it:

- The controller takes `analysisId` as a plain `String` and calls a service.
- **`AnalysisService.requireCompleted(analysisId)` is the single gate.** It enforces **ownership** (the analysis belongs to the caller, else 404, admins included), parses the id strictly as a canonical UUID, and throws `AnalysisNotFoundException` (404) or `AnalysisNotCompletedException` (409, also for `FAILED`). `GraphService` calls it first and passes `uuid.toString()` to Neo4j, because that string is the `analysisId` stored on every node.
- Neo4j reads live in `graph/GraphQueryService` and `graph/CodeQueryService`. Cypher is built only from fixed strings and the label/relationship enums; ids, filters and paging are always bound parameters. Postgres reads go through `analysis/` services.
- **Node ids** (`class:com.foo.A`, `file:src/A.java`, `method:com.foo.A#m(String)`) are the API's `nodeId`/`fileId`/`classId`. The prefix is the node type; an unknown prefix is a 404 without a query. They contain `/`, `#`, `(` and spaces, so clients percent-encode them, `common/TomcatConfig` passes `%2F` through and `SecurityConfig.httpFirewall()` allows it. Without both, ids with a `/` never reach the controller.
- **External nodes** (`external: true`: library types, external modules) exist in the graph but are never returned or counted, except as labelled targets in `imports`/`references` and in a class's `superclasses`/`interfaces`.
- Lists paginate with zero-based `page` and `size` (default 50, at most 200; out of range is a 400). Filters combine with AND.
- **Every endpoint that returns graph or file nodes must populate `test` through `common/TestPathClassifier`** (never a second copy of the rules). It is computed at read time from the stored `file` path, so it works on old analyses; `Method`/`Function`/`Class`/`Interface`/`File` nodes carry `file`, a `Module` is a test only if it has files and all are tests (read with the node), the `Repository` never is. `GET /files?test=true|false` needs the flag before paging, so with `test` the matching rows (id, name, path, language) are classified in Java and then paged; without it the paging stays in Cypher. Changing the rule table means changing `TestPathClassifierTest` and the table in `Architecture.md`.

## Neo4j rules

- Graph code lives in `graph/` and uses `Neo4jClient` and Cypher only. Spring Data Neo4j repositories are off (`spring.data.neo4j.repositories.type=none`) so they do not scan the JPA repositories.
- Every node carries `analysisId` and every query filters on it. Labels and relationship types match the root `CLAUDE.md` exactly; add new ones to `Architecture.md` first.
- Node ids are stable, derived from the analysis plus a qualified name. Never expose Neo4j internal ids.
- Write in batches (`UNWIND $rows ... MERGE`), not node by node. Map results into the React Flow `{ nodes, edges }` DTO in `graph/`; keep the mapper parameter-driven for V2 (`rootNodeId`, `depth`, `maxNodes`).
- PostgreSQL holds only metadata, accounts and tokens; code entities never go into it.

## Ask AI (`ai/`)

Repository-aware chat. Full design: `spec/ask-ai-backend/spec.md`; decisions and API: `Architecture.md` → Ask AI.

- **The pipeline never waits for AI, and AI never fails an analysis.** `analysis/` publishes events defined in `common/` (`AnalysisGraphBuilt` with the clone root, `AnalysisCompleted`, `AnalysisFailed`, `AnalysisDeleting`); `ai/` listens in `ai/AiAnalysisEvents`, `analysis/` never imports `ai/`. `AnalysisGraphBuilt` is handled **synchronously while the clone still exists** (chunk text is captured then, because the clone is deleted in `finally`) and its listener must never throw (any error becomes a FAILED index); the pipeline also guards it. Embedding runs after `COMPLETED` on `aiIndexExecutor` (one worker). `AnalysisDeleting` is published before the row is deleted and **may** throw: the delete then stops and the row stays.
- **Index lifecycle** (`ai_index`, `code_chunks`): no row is `NOT_INDEXED` (analysed before the feature: re-analyze, no backfill); `INDEXING` → `READY`; `FAILED` is retryable for free only when chunks exist; `EMPTY` means only test code. Status changes are guarded UPDATEs (`WHERE status = ...`) so a late job cannot resurrect or overwrite a row. `IndexRecovery` drops the data of analyses that did not complete and resumes `INDEXING` rows (startup and a sweep); a job continues where it stopped (only chunks without a vector). Test code (`TestPathClassifier`) is never indexed, retrieved or cited.
- **Chunk kinds** are `TYPE_HEADER`, `METHOD`, `FUNCTION` and, for the repository node, `README` and `MANIFEST` (`ProjectDocs`, captured in the same synchronous `AnalysisGraphBuilt` handler, after the cap, only when there is code, never throwing; text never logged). They are searchable but **never seeds for graph expansion**; `code_chunks.kind` is a string with a CHECK that `CodeChunkSchemaUpgrade` widens, and nothing may switch exhaustively on the kinds. Grounding verifies `REPOSITORY` and `MODULE` sources through `RetrievalGraphService.citableNodes`.
- **Chunks and vectors are plain SQL** (`ChunkStore`, `ChunkSearch`), never loaded as entities; `CodeChunk` exists to define the table. Spring AI is used for `EmbeddingModel` and chat only, not `PgVectorStore`. No vector index in V1 (exact cosine scan of one analysis). The vector size is `EmbeddingSpec.DIMENSION` (384) and also the column's: startup fails if the model differs.
- **Retrieval** (`ai/retrieval`) is deterministic and has a fixed priority: name matches, graph facts, vector hits, neighbours, sticky (nodes the previous answer cited). **Overview questions** (`QuestionIntents`, fixed whole-phrase rules, no model) take another road: `ProjectContext`'s pack (identity, technologies, counts, most depended-on classes, biggest modules, each citing its node; identity never dropped), then the README and manifest chunks, then at most 4 vector hits, fitted so the README is truncated first, then modules go. Every question also gets an unnumbered preamble line. The answer cache key includes the intent. Graph reads are `graph/RetrievalGraphService` only (fixed Cypher, bound parameters, `analysisId` on every query, external and test nodes dropped). Only the best `vector-seeds-expanded` vector hits are expanded into facts, because facts rank above chunks and would otherwise fill a small budget.
- **Never call a provider directly: only through `ProviderGateway`** (full design: `spec/ask-ai-providers/spec.md`, `Architecture.md` → Ask AI provider chain). It walks the chain from `archyra.ai.providers.order` within `timeout.total`, at most `providers.max-attempts` providers per question, never the same provider twice, and gives each attempt a share of the time left (the gateway caps it itself: the Gemini SDK's own timeout did not cut a slow call). No retries anywhere (one attempt; `RetryPolicy.withMaxRetries(0)` for Gemini). The prompt is built **per provider** with that provider's `max-context-tokens`. Model ids, limits, base URLs and keys are configuration only, never Java literals, and provider ids are free-form strings (never an enum: `chat_messages.provider` is `varchar(40)`).
- **A provider is a config block, not a class.** `ProviderRegistry` binds `archyra.ai.providers.<id>.*` with the `Binder` (`order` and `max-attempts` live beside the id blocks, so a `Map` binding would not work). To add one that speaks OpenAI chat completions: one block in `application.properties` (display name, base URL, `api-key=${..._API_KEY:}`, model, `max-context-tokens`, the local limits, `logs-prompts`) plus its id in `order`, then its key in `.env.example` and a row in the README table. `OpenAiCompatibleChatProvider` is a plain `RestClient` so the rules below hold: it reads only `choices[0].message.content` (never `reasoning_content`), classifies by status and `Retry-After` and never keeps a response body. Anything with a different wire format needs its own small adapter (`GeminiChatProvider`).
- **Safety rules live in code (`ProviderRules`, `ProviderRegistry`), not only in properties**: OpenRouter refuses startup unless its model ends in `:free`; OVH is anonymous only (`auth=none` is forced, no `Authorization` header is ever sent, a key is ignored with a warning); Cohere warns at startup (non-commercial); the opt-in providers (`nvidia-nim`, `kilo`, `gonka`) are off unless `enabled=true` is set explicitly; two active providers with the same key refuse startup; a key only ever goes to its own provider. A provider that is disabled, key-less or has an unusable base URL is simply not in the chain: never fail startup for a missing key. `ProviderChainTest` pins every one of these; keep it passing when you touch the registry.
- **Local limits are per provider and in memory** (`ProviderGuard`: Bucket4j for requests/min, a semaphore for calls in flight released when the call really ends, UTC day and month counters). A local refusal skips the provider and is **not** an attempt; the pre-flight check treats a locally exhausted provider like a cooling one. Failures: 429 → `ProviderCooldowns.rateLimited` (Retry-After, else a default that doubles on every repeated 429 up to `cooldown-max`; a success resets it), 401/402/403 and 404 → `misconfigured` (long cool-down, `ERROR` log), 5xx/timeouts/empty answers → next provider with no cool-down. Output goes through `AnswerText.clean` (think blocks removed, trimmed; empty = failure) for every provider.
- **The test profile switches the local limits off and OVH off** (`application-test.properties`), because tests ask dozens of questions within a minute and OVH needs no key; tests of limits bind their own through `ProviderKit` (the real registry, cool-downs and gateway on `FakeProviders`, no Spring context). Provider tests use `FakeProviders` (one WireMock server per provider; `holdRequests` latches keep a call in flight, `answerWithRawBody` sends any 200 body) and a `MovableClock`, never sleeps.
- **Grounding** (`chat/Grounding`, `ChatService`): the model sees numbered items and never a node id. `[n]` markers outside code are read (also fullwidth `【n】`, which Groq's model writes; they are rewritten as `[n]`), numbers that are not items are dropped, the rest renumbered by first appearance, and **every source is re-verified in Neo4j** (a marker whose nodes vanished is dropped too). Repository text is untrusted data: it sits inside `<repository_context>` tags and a closing tag inside a chunk is defused.
- **Quota** (`chat/ChatTransactions`): reserve one `AI_QUERY` (a **weekly** allowance, see Usage limits) **before** the model call (`UsageService.lock` + `charge` in one transaction with the PENDING user message, which also stores the window charged in), no transaction while retrieval or the model run, then answer (`complete`) or **refund exactly once** (`UPDATE chat_messages SET quota_refunded = true WHERE id = ? AND quota_charged AND NOT quota_refunded AND status = PENDING`; only the winner calls `UsageService.release(.., window)`, a no-op if the week has turned). The `PENDING` condition is what stops a late failure from refunding an answered question. A cache hit stores both messages and is free. `ChatRecovery` refunds PENDING messages at startup; `ConversationService.purge` (analysis deleted or failed) refunds them before deleting. `ChatMessage` is `@DynamicUpdate`. Order of `ChatService.ask`: validate (no side effects) → cache → **retrieve (free)** → reserve → prompt per provider/call/ground → persist; anything after the reservation refunds. **A question with no usable context is a `422 QUESTION_NOT_ANSWERABLE` before the reservation** (nothing sent, counted or stored; the rate limit is still consumed): `RetrievedContext.usable` is true only when a node is named or some chunk is at least `min-similarity` close (calibrated: 0.23, see `Architecture.md` → Ask AI and `QuestionCalibrationIntegrationTest`), or, for an overview, when the analysis has a graph.
- **Never log question text, code, answers, provider response bodies or keys.** `ChatService` logs only user id, analysis id, provider, latency, outcome and cached. The retry template under Spring AI's Gemini model logs the SDK exception (whose message carries the provider's body) at DEBUG, so `application.properties` pins `logging.level.org.springframework.core.retry=INFO`. A `ProviderException`'s cause can carry a provider's error body: never log or return it, and never put it in a message. Error bodies are fixed text.
- **The ONNX session is native memory: never close it under a running inference.** `EmbeddingService` takes a read lock around every batch and `destroy()` a write lock, and `EmbeddingJobs` stops quietly on `EmbeddingClosedException` (the index stays INDEXING and resumes at the next start). Closing a Spring context while an embedding job ran used to crash the whole JVM (SIGSEGV in `libonnxruntime`).
- **One question at a time per conversation** (`ChatInFlight`, in memory): `CONVERSATION_BUSY`; deleting a busy conversation is refused too. PENDING messages are never listed and never part of the history. History goes back without sources, within `history.turns` and `history.max-tokens`.
- **Tests**: `AiIntegrationSupport` (real pipeline, parser, PostgreSQL with pgvector, Neo4j, the real ONNX model; only `GitCloner` is replaced) and `ChatIntegrationSupport` (plus `FakeProviders`: WireMock as the fake providers, speaking the real wire formats, answers computed from the received prompt). Faults are injected with real database constraints (`ALTER TABLE ... ADD CONSTRAINT ... NOT VALID`), not mocks; races use latches and barriers. These classes close their Spring context after the class (`@DirtiesContext`), `src/test/resources/spring.properties` bounds Spring's context cache (`maxSize=6`) and `TestcontainersConfiguration` caps Neo4j's heap and page cache: every context holds a PostgreSQL and a Neo4j container, and dozens alive at once exhausted an 8 GB Docker VM, so the kernel OOM-killed Neo4j containers (Docker reports `oom`, exit 137) and the next test that reused that cached context failed with "connection refused" (it also killed a developer's own Neo4j container once). The first run downloads the embedding model (about 90 MB, into `models/`). `AiLiveSmokeTest` (opt-in, `ARCHYRA_AI_LIVE_TESTS=true`) asks one trivial question per provider whose key is set (skipped silently otherwise) and one real grounded question.

## Tree-sitter rules

- Tree-sitter types stay inside `parsing/`. Extractors turn ASTs into IR; everything downstream depends only on the IR.
- One extractor per language behind `LanguageExtractor`, by extending `TreeSitterExtractor`. Adding a language must not touch the graph builder or the resolver. Extractors walk the tree through the base-class hooks, not `.scm` queries; print a real parse to check node and field names instead of guessing.
- Binding is the official `jtreesitter` (FFM API). Do not switch to JNI bindings (reasoning in `Architecture.md` → Technologies → Notes). Upgrading it may raise the minimum Java version, so check its `maven.compiler.release` first.
- It ships no native code: the runtime and grammars are built by `scripts/build-native.sh` and loaded only by `parsing/NativeLibraries`. Any launcher needs `--enable-native-access=ALL-UNNAMED` (already set for Surefire and `spring-boot:run`; a jar or Docker entrypoint needs it too). Packaging the libraries for deployment is still to do.
- `ReferenceResolver` resolves calls, type usages and imports after every file is parsed. Targets outside the repository become `external` nodes; a reference tied to nothing known is counted and skipped, never guessed.
- Parsing one bad file must not fail the analysis: log it, record it, continue.

### Languages and technologies

- **Analysed** (classes, functions, imports, calls): Java, Kotlin, Python, JS/JSX, TS/TSX, Go, Rust, C#, PHP, Ruby, Solidity, Vue and Svelte (`<script>`), Jupyter notebooks. **Counted only**: Swift, Dart, C, C++, Scala, R, Julia, shell, SQL, HCL, Dockerfile, HTML, CSS.
- Extractors implement only the hooks their language has; never force one language's concepts into another (free functions are `Function` nodes, not fake classes).
- **IR contract:** a file has a `moduleName` (what qualifies its symbols and what imports name) and a `packageName` (the Module node grouping). A type is `FULL`, `PARTIAL` (C# `partial`, Ruby open classes) or `EXTENSION` (Go receivers, Rust `impl`). `ModuleResolver`s map import specifiers to modules; `ReferenceResolver` itself has no language rules.
- **To add a language:** (1) a row in `GRAMMARS_TABLE` of `scripts/build-native.sh`; (2) the `Language` value and extensions in `ingestion/LanguageDetector`; (3) an extractor `@Component` in `parsing/lang/`; (4) a `ModuleResolver` only if imports differ from "the import names the module"; (5) a fixture under `src/test/resources/fixtures/polyglot/<language>/`, a test on `FixtureAnalysis`, and the new classes in the test helper `Languages`; (6) rows in `src/main/resources/technologies.tsv`.
- **Technologies** are detected best-effort (and can never fail an analysis) from files, manifests, framework languages and imports. A framework is a tab-separated row in `technologies.tsv`, not code. They are stored in `analysis_metadata` and returned by `GET /repository` as `technologies` (`codebase/RepositoryService` maps `AnalysisMetadataService.getTechnologies`, already ordered by category then name, to the feature's own `TechnologyResponse`; name and category only, never the evidence file or ecosystem; always a list, empty when nothing was detected). `RepositoryEndpointIntegrationTest` pins the shape, the order, the empty list and the 404 for another user's analysis.

## Security

Summary; the full design is in `spec/security/design.md`, requirements in `spec/security/spec.md`.

- Two filter chains: the stateless API chain (`security/SecurityConfig`, JWT resource server) and a handshake-only chain for `/oauth2/**` (`auth/oauth2`). Everything under `/api/v1` needs a token except the public `/auth/**` routes. Admin routes need ROLE_ADMIN and are re-checked against the database.
- Access tokens (15 min, HS256) come only from `JwtService`; `sub` is the user id and the plan is never in the token. Refresh tokens are opaque, hashed, rotated, and sent in an `HttpOnly; SameSite=Strict` cookie; refresh and logout are the only CSRF-protected routes.
- **Account linking (Settings → Sign-in methods) is a separate mode of the OAuth handshake, not a login.** `LinkAuthorizationFilter` (before Spring's redirect filter) turns a valid `link_intent` **plus the matching `link_binding` cookie** into a link context in the handshake session; **never relax the cookie check** (without it a crafted URL attaches a victim's provider identity to an attacker's account). In link mode the user-info services return a `LinkPrincipal` and **must not call `SocialAccountResolver`** (it would create, email-match or take over accounts); `OAuth2LinkHandler` takes the user from the session, issues no tokens or cookies and ends the session. Link/unlink logic and its emails (sent after commit, never failing the operation) are in `user/IdentityLinkService`, which locks the user row. `hasPassword` is `passwordHash != null`. Details: `Architecture.md` → Linked sign-in methods, `spec/security/design.md` §6.
- **Changing the password from Settings** (`POST /users/me/password`, `auth/PasswordController` + `PasswordChangeService`) must keep three properties: the **current password is always verified** (a bearer token alone must not be enough), a wrong one **counts towards the same lockout as a failed login** (that, not a rate limit, bounds guessing), and success **revokes every refresh family and starts a new one for the caller in one transaction**. The wrong-password failure is recorded *outside* that transaction (`recordFailedLogin` has its own), so do not wrap the whole method in `@Transactional`: the throw would roll the failure count back. An account without a password gets `409 NO_PASSWORD_SET` and uses Forgot password: do not let a bearer token set a first password. Details: `Architecture.md` → Change password.
- **Deleting the account** (`POST /users/me/delete`, `/delete-request`, `/delete-confirm`; `auth/AccountDeletionController`, `AccountDeletionFlows`) follows the change-password rules: a bearer token alone is never enough. A password account sends its password (a wrong one counts towards the login lockout, recorded outside the deletion transaction, so the flow itself is not `@Transactional`); a password-less account confirms with an emailed one-time token (`ACCOUNT_DELETE`, 15 minutes, consumed in the same transaction as the deletion so a refusal leaves it usable); the wrong flow is `400 DELETE_METHOD_MISMATCH`; the last enabled admin is `409 LAST_ADMIN`. Details: `Architecture.md` → User → Delete account.
- **Register never reveals whether an address is registered**: same `202` and body for a new and an existing address, no `409`. An existing address is handled afterwards by `auth/ExistingAccountFlows` on the mail executor (verified: an "account already exists" notice via `EmailService.sendAccountExistsNotice`, at most one per address per hour through `RegisterNoticeThrottle`, links without a token; unverified: a fresh verification link and the stored name and password are *not* replaced; disabled: nothing), with a `REGISTER_EXISTING_ACCOUNT` audit line. Do not add a `409`; the reasoning is in `spec/security/design.md` §4.
- **Ownership is enforced in `AnalysisService` only**; a new endpoint must go through `requireCompleted`. Foreign and unknown ids both give 404.
- **Premium is read from the database** by `EntitlementService` (never the token). `graph/GraphPremiumGate` lets FREE use no parameters, `nodeType`, `relationshipType` and `level=BEGINNER`; everything else is `403 PREMIUM_FEATURE`. New V2/V3 endpoints call `requirePremium(Feature)` themselves.
- Rate limits, the audit log (`security.audit`, never a secret), token purge and admin bootstrap are described in the design document.
- **Tests:** slices import `security/SecuritySliceConfig` and use `@WithMockUser`; real-HTTP tests mint tokens with `JwtService`; `EveryEndpointIsProtectedTest` fails if a new endpoint is left open. A new public endpoint must be added to its explicit list.

## Testing

- Language tests run the real parser over `src/test/resources/fixtures/polyglot/<language>/` through `FixtureAnalysis` (no Spring); they need the native libraries.
- Tests that load the Spring context use Testcontainers (`TestcontainersConfiguration`, `@ServiceConnection`, profile `test`) and need Docker. Pipeline integration tests run the real pipeline against real PostgreSQL, Neo4j and parser; only `GitCloner` is mocked (it copies fixtures such as `sample-repo`).
- Endpoint tests come in three layers: `@WebMvcTest` controller tests with a mocked service, Mockito unit tests of services, and integration tests. Tests that need ids containing `/` (`NodeEndpointHttpTest`, `FileAndClassEndpointHttpTest`) use `RANDOM_PORT` and a real `HttpClient`, because MockMvc skips Tomcat and would not notice the `%2F` setting being removed.
- Mockito runs in strict-stubs mode: an unused stub fails the test. A shared `setUp` stub that only some tests use needs `lenient()`.
- Do not name a test helper `get`, `post` or `delete` in a class that statically imports MockMvc's: it silently shadows them (use `getAs`, `postJson`).
